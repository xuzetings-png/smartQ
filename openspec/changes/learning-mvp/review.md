# 技术方案评审记录：learning-mvp

日期：2026-09-24。首轮评审已通过并进入实现；剩余事项在相关功能开发前确认，并同步到设计和规格。

## 已确认决议

### 1. 开发验收主线

本期以五个场景判断问数链路是否完成：

1. 按城市查询销售额，并展示 SQL、结果表和柱状图。
2. 对“今年”等重要歧义先澄清，确认后才执行查询。
3. 在同一会话追问“哪个城市最高”，继承上一轮资源和查询条件。
4. 查询无匹配数据时明确显示空结果，不编造数值。
5. 模型故障或越权字段被明确拒绝，并显示可理解的失败阶段。

演示题目的精确措辞、合成数据中的预期结果和错误注入方式，将在本轮评审结束后固定。

### 2. 样例问题调试入口

管理员在问数资源配置页内调试样例问题，查看查询计划、字段映射和校验结果。继续使用 `POST /api/resources/:resourceId/plan-preview`；不设置独立调试页面。

### 3. 演示销售额口径

“销售额”固定表示已支付订单的 `amount` 合计，即 `SUM(amount)` 且 `status=paid`。取消和退款订单不计入销售额。该规则必须在查询计划校验和服务端 SQL 编译中生效，不能只由模型在提示词中猜测。

### 4. 指标规则配置位置

管理员在资源配置页维护“销售额”的指标规则。技术设计需增加业务指标定义、规则校验和持久化约定，让前台查询使用保存后的规则。

### 5. 已发布指标规则不可临时覆盖

问数用户不能用自然语言覆盖已发布指标的固定条件。若问题要求“包含退款的销售额”，系统说明“销售额”只计已支付订单，并建议改问“订单金额”；不得静默改变销售额口径。

### 6. 单次查询的指标数量

第一版一次自然语言查询只处理一个指标。多指标对比留到后续变更；查询计划、SQL 编译和图表契约据此收敛。

### 7. 结果说明生成方式

服务端根据通过校验并实际执行的查询计划与结果，生成固定、可追溯的文字说明；不额外调用模型生成分析结论。

### 8. 澄清后的最终规划

首次澄清仅返回问题、选项和是否支持自由文本，不要求模型为每个选项生成完整 SQL 查询计划。用户确认后，服务端把原问题、澄清问题及用户所选答案或自由文本再次交给模型，取得最终 JSON 计划并重新校验，确认前不访问 MySQL。

### 9. 开放字段的受控聚合

用户可以对管理员标记为可问的指标字段使用其允许的聚合方式，例如 `AVG(amount)`。命名业务指标作为另一种明确的查询对象，使用管理员保存的聚合和固定过滤规则；问数计划必须区分“开放字段聚合”和“命名指标”，且两者都只允许当前资源的白名单字段。

### 10. 问数前检查源表结构

每次问数在调用模型和执行查询前，比对当前 MySQL 表结构与已发布资源的结构摘要。若字段类型、名称等发生变化，系统把资源标记为待复核，并暂停本次问数；管理员复核后才能继续。

### 11. 相对时间的演示日期

服务端使用 `SMARTQ_DEMO_DATE` 作为相对时间解析基准；未配置时使用真实当前日期。日期基准及 `Asia/Shanghai` 时区随规划上下文提供给模型，便于面试演示复现同一时间范围。
